## 资源监控为何没有有效接住

运行入口为 `~/Library/LaunchAgents/com.tianli.resource-watch.plist`，实际指向本仓 `deploy/com.tianli.resource-watch.plist`；不在 `/Library/LaunchDaemons/`。当前 ctl 回读运行中。

1. 每 15 秒采样，CPU ≥90% 或内存 critical（4）连续 60 秒才提示；任何一次不满足便重置。长期 60%–85% 和 warning（2）不触发，WindowServer 单独占多个核心也没有独立条件。
2. 17:14:48 的 actions 记录 `overload_prompt`，CPU 98.11%、内存 warning。随后至少到 17:44:48 处于 30 分钟冷却；提示 90 秒后自动消失。无退出应用请求记录。
3. 这条事件不能证明用户看到弹窗：代码先设置冷却，`try? task.run()` 吞掉启动异常，仍写 `overload_prompt`。取消、超时、显示成功、启动失败均无独立记录。旧 stderr 有旧路径 sandbox 错误，但无时间戳，不能据此认定当次提示失败。
4. 只有用户勾选确认后才请求普通 GUI App 正常退出；系统服务和后台任务只展示。没有自动降低 CPU/内存或暂停任务的机制，不能把 launchd 托管等同于资源治理。
5. 即便因内存触发，也按 CPU 排前 15 项、弹窗只展示前 8 项，可能漏掉低 CPU 的内存大户。RSS 总和只是估算，含共享页重复。
6. 事发版本用 `ps pcpu` 且没有 PID，进程值与整机采样窗口不同，不能直接相加。9/14 23:46:33 的 `4e5e2f3` 才补 CPU 时间差、PID、受管任务归属；未改变以上告警与弹窗缺口。历史 Python 分组也不能全部回填成图谱服务。

源码定位：`scripts/system/resource_watch/main.swift` 的提示呈现、退出请求及阈值/冷却逻辑；`ProcessSampling.swift` 的分组与排序。独立只读复核确认上述缺口。现有测试覆盖采样归属，不覆盖完整告警生命周期。

## 本会话处理不足

- 第一时间没有读取现成资源监控的历史记录，导致依赖零散现场快照，错过长达约一小时的唤醒后异常。
- 把结束进程、降低某项空闲 CPU 与整机恢复区分得不够清楚；搜狗恢复、Spotlight 修复、最后负载下降均没有形成完整因果证明。
- 外屏数量是排查线索，不是根因。今天相同屏幕配置低占用是直接反证，应保留“绘制路径异常，具体来源未定位”的结论。
- 在未查进程树前短暂暂停 Ghostty，影响了包含当前会话的宿主；后续必须先确认宿主与任务依赖，沿用用户保留终端任务的要求。

## 最小改进方案（尚未实施）

- 分离持续警告与严重过载：对长期 warning、窗口绘制异常和持续中高 CPU 建独立条件，用时间窗口/迟滞避免一次低采样清零。阈值通过本次历史回放确定，避免 warning 常态造成提示轰炸。
- 提示留持久建议；记录启动失败、已呈现、超时、取消、请求及结果。启动失败不消耗正常 30 分钟冷却，并对反复失败做限频重试。
- CPU 和内存分别排序；系统绘制异常给针对性诊断步骤。终端及其任务默认保护，不以自动关应用代替定位。
- 对明确允许延迟的自有后台任务按任务策略退让，如本轮已做的图谱调频；普通应用仍需用户确认退出，不对所有进程统一强杀。
- 增加告警策略、冷却与提示生命周期的测试和本次历史回放验收。自动处置与告警建议的边界需清楚显示。
